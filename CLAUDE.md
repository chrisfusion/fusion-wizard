# fusion-wizard

Kubernetes-native Go backend (operator + REST API) that orchestrates multi-service provisioning across
fusion-forge, fusion-index and fusion-weave (dir `../fusion-flux`), replacing the browser-side
orchestration in spectra's wizards (`useGitAppProvisioning.ts`, kept as proof of concept). Called by the BFFs.
Structural template is `../fusion-flux` (operator + api-server binaries, chart, auth); each sibling's
CLAUDE.md is authoritative for its own REST shapes. Module `fusion-platform.io/fusion-wizard`, GPL-3.0.

## Commands
- `make generate` — deepcopy + CRDs to `config/crd/bases/`; `make sync-crds` copies into the chart's `crds/` (manual: Helm never updates `crds/`); `make check-crds` diffs the two
- `make test` (`-race`, required: ledger/reconciler are concurrent); `make build`; `make docker-build` (minikube daemon, semver tag)
- Validate CRDs without persisting: `kubectl apply --dry-run=server -f config/crd/bases/`
- Go dependencies are vendored and committed (`vendor/`, ~57 MB on disk, ~7 MB in git) because the CI environment that builds the images has no internet access (builds must not download anything). `make build`/`test` and the Dockerfile use `-mod=vendor` (the Dockerfile has no `go mod download`). After any `go.mod` change run `make vendor` and commit `vendor/` with `go.mod`/`go.sum`; `make check-vendor` fails on drift. `vendor/**` is `-diff linguist-vendored` in `.gitattributes`. The only external inputs left are the Docker base images (`golang:1.25-alpine`, `gcr.io/distroless/static:nonroot`) — mirror them in an internal registry or `docker save`/`docker load` them. Verify with `docker build --network none .`
- Local `go` is 1.22 but `go.mod` needs 1.25 — `GOTOOLCHAIN=auto` uses the cached toolchain; `controller-gen` is `~/go/bin` v0.16.1

## Design invariants (agreed, don't re-litigate)
- CRDs (`wizard.fusion-platform.io`): `WizardDefinition` (instance-agnostic recipe), `WizardRun` (state), `WizardResource` (ledger). Not built on weave.
- Step order is fixed (`gitWatcher, waitBuild, tag, app, jobTemplate, serviceTemplate, chain, trigger, batchTrigger`); a definition picks a subset in that order.
- `app` step (added 2026-10-20, on weave 0.6.0's `WeaveApp`): ONE `WeaveApp` (`POST /api/v1/apps`) per service/job that owns its Deployment/Service/Ingress/Jobs, so `image-service`, `image-job`, `image-cron-job`, `python-git-job` and `python-git-service` have no template/chain/run/trigger and share nothing between runs; deleting the app is the whole teardown (undo rank 5). Mode follows `artifactName`+`tag` (both or neither): with them `codeSource` on the instance runner image (image is an instance default, NOT in the ledger hash), without them the caller's `image` (immutable tag/digest rule via `validateImmutableImage`, IS in the hash). Job apps: `entrypoints` param = the whole objectList as JSON (`${params.entrypoints}` renders it; each entry -> weave entrypoint `k8sName(stem(key))` capped at 40, env `ENTRYPOINT=<key>`, `schedule` only for Cron) OR a single `main` entrypoint with optional `schedule` and `fireOnCreate`. `fireOnCreate` = the `fusion-platform.io/fire` annotation on the CREATE body (weave consumes it), so it only fires on a real create, never on adopt. Schedules are weave's 6 fields, seconds first. WeaveApp has no `imagePullPolicy`, no per-entrypoint `externalAuthRef` override (one app-level ref, jobs only; services reject it), and no BatchCron/Kafka — hence `batch-git-job`/`batchcron-git-job` keep template+chain+trigger. `ALLOWED_IMAGE_PREFIXES` gates app images but an EMPTY list means unrestricted (opposite of run overrides). `steps.ValidateAppParams` runs at run creation; params that depend on step output/config are passed as `steps.Pending` and skipped (the API must NOT drop the whole step as it does for other types, or an entrypoint typo would only surface after the build)
- Trigger step `fireOnCreate: "true"` fires the trigger once, right after the call that actually creates it (never on adopt/re-confirm) — added 2026-09-22 so `batch-git-job` can replicate spectra's "starts once immediately" wizard behavior.
- `objectList` parameter type (added 2026-09-22): a JSON array of flat string-keyed objects, the second forEach source alongside `stringList`. Every entry needs a non-empty `"key"` field — it's both the forEach instance's identity (bare `${item}` still means "this entry's key", exactly like a plain stringList item, so existing patterns like `${item|stem|k8sName}` keep working unchanged) and, by convention, what an author names the entry after. Other fields read with `${item.<field>}` (`internal/params/template.go`'s `Context.ItemFields`) — every entry should carry the same set of fields, `""` for one that doesn't apply; there is no per-field default, referencing a field an entry omits is an `UnresolvedError`. This is what lets `python-git-job`'s `entrypoints` carry a per-entrypoint `type`/`schedule` (mixed OnDemand/Cron in one run — `internal/controller`'s `TestMixedOnDemandAndCronEntrypoints` proves it end to end), where a plain stringList forEach could only ever give every expansion the identical `type`/`schedule` value.
- `batchTrigger` step (added 2026-09-22, unblocks BatchCron): creates a single BatchCron `WeaveTrigger` through weave's dedicated `POST /api/v1/batchtriggers` (also provisions the jobs ConfigMap) instead of the generic trigger endpoint, since the generic one can't carry an inline job list. Never `fireOnCreate` — BatchCron entries each start on their own internal schedule (weave's scheduler), applying the fire annotation goes through an unrelated weave code path that creates a bare run with no per-entry context. `jobs` is opaque text the wizard never parses; weave validates it at creation time, so a malformed blob fails the step with weave's own error message (loses the old wizard's field-level pre-validation). The dedicated create endpoint has no labels field, so managed-by labels are stamped by a **second** call (`PatchLabels`, generic trigger PATCH) right after a successful create — same "only on real creation" guard as `fireOnCreate`. Conflict detection (`matches`) only checks `type`/`chainRef.name`, not the actual jobs content (which lives in a ConfigMap, not directly comparable without an extra fetch) — narrower than every other step's guarantee; documented gap, not fixed.
- Removed 2026-10-20 (superseded by the `app` step): the `run` step (WeaveRun with `stepOverrides`/`imageOverrides`), the `trigger` step's `image`/`imagePullPolicy`/`stepName`, and the shared image-only template/chain design of `image-service`/`image-job`/`image-cron-job` (`git log` has it). `jobTemplate`/`serviceTemplate` still accept the image-only mode (no `artifactName`/`tag`), now unused.
- `externalAuthRef` (weave's short-lived SA/OIDC token injection into Job pods; added 2026-09-29) is opt-in: `chain` params `externalAuthMode`/`externalAuthName` -> `spec.externalAuthRef`, `trigger` params `externalAuthOverrideMode`/`externalAuthOverrideName` -> `spec.externalAuthRefOverride` (weave applies run > trigger > chain). Both-or-neither, mode `serviceAccount`|`oidc` (the API rejects a bad pair with a 422 at run creation via `steps.ValidateExternalAuthParams`, only for params resolvable from run parameters/forEach items); the name is NOT checked by the wizard, and weave does not reject a bad one at create time either: it marks the chain `status.valid=false` (chain level) or fails the run when it fires (trigger override) — so the step still succeeds; the GUI must only offer names from the picker (`GET /api/v1/external-auth/options` on weave; the wizard does not proxy it). Deliberately absent for service (Deploy) chains — the chain step rejects it, because a minted token would expire under a long-running deployment — and for `batchTrigger` (the dedicated endpoint can't carry it; `batchcron-git-job` only exposes the chain level). `unsafeEnvironmentInjector` is not exposed (weave default stays on). Included in the ledger hash only when set, so pre-existing entries keep their hash.
- `gitWatcher` param `autoPromote: "true"` (added 2026-10-20; chart Git definitions expose it as a boolean parameter, default `true`) sets forge's `GitWatcher.spec.autoTag` (forge >= 0.11.0) to the run's tag (`tag` param, else instance `tagName`), so FORGE moves the tag to every later build — the wizard's `tag` step still covers the first build, and runs stay terminal (the wizard never watches builds after Ready). Weave already follows a moved tag (`WeaveApp` re-resolves it every `CODE_SOURCE_POLL_INTERVAL` and rolls the pods). The auto-tag is in `matches` AND (only when set) the ledger hash: an existing watcher with a different auto-tag is a conflict (user's decision, consistent with "no silent update") — including every watcher created before this change, until its `auto_tag` is PUT in forge
- Per-instance values (runner image, resources, tag name, polling) come from a Helm-rendered ConfigMap at run time; precedence: run input > definition default > instance config.
- `WizardRun.spec.definitionSnapshot` is what runs and rollbacks use — never re-read the live definition mid-run.
- Ledger: every managed resource is ref-counted. Delete upstream only when the last ref is gone AND `managed: true`. Set `terminating` (resourceVersion-guarded) before deleting; adopters must not adopt a terminating entry. Found-without-ledger resources are `managed: false`, never deleted. Same name + different `specHash` = visible conflict, no silent update.
- Undo order is NOT blind reverse: by resource kind (`undoRank`, `internal/steps/rollback.go`): trigger, chain, template, **watcher**, tag, artifact — delete the watcher before the artifact or forge rebuilds it.
- Rollback is driven by the LEDGER (`Env.Rollback(run)` finds every entry referencing the run), never by run status: a step that failed midway holds a ref but is not in status. `SweepTerminating` finishes deletions a crash interrupted.
- `ensure()` is write-ahead: ledger entry first, upstream create second. A step's identity = the settings that define it (template: artifact+tag; NOT image/resources, which are instance defaults).
- Reconciler (`internal/controller`): one status `Patch` per reconcile, skipped when nothing changed (no write loops); the update predicate ignores status-only changes, polling is `RequeueAfter`; the retry annotation is removed only AFTER the reset status was written; a rolled-back run is terminal (create a new run).
- API (`internal/apiserver`): validates on create what the reconciler would validate later (definition, parameters, `plan.Expand`) so clients get every problem as one 422 with `details`; errors are `{"error","details"}` (spectra reads `body.error`); refuses to start without `AUTH_ALLOWED_SA` (no "any service account" mode); user headers are read only after the caller passed the allowlist; bulk rollback requires a selector and caps targets at 200.
- Operator calls upstreams (SA token re-read per request); api-server only reads/writes CRs. Identity (creator self-delete, privileged bulk delete) is deferred; API stamps `createdBy` from `X-User-ID` only for allowlisted BFF SAs.
- Every upstream resource the wizard creates is stamped `fusion-platform.io/managed-by: wizard` (platform-wide, open-valued — other components may use their own value, e.g. a future "manual" default) and `wizard.fusion-platform.io/run: <run-name>` (scoped, since weave already uses the unscoped `fusion-platform.io/run` for a different concept). Lets a raw `kubectl get -o yaml` answer "is this wizard-managed" without the ledger API — for warning a user before they hand-edit a chain or similar. `internal/ledger.LabelManagedBy`/`LabelRun`; applied in `weavesteps.go`'s `stampOwnerLabels` (jobTemplate/chain/trigger — one shared call site) and threaded to forge via `CreateGitWatcherRequest.Labels` (forge's `POST /api/v1/gitwatchers` accepts it as of 2026-09-22; its `PUT` never touches `ObjectMeta`, so labels survive updates).

## Gotchas
- Adding a new step type touches ~9 places: CRD enum (`api/v1alpha1/wizarddefinition_types.go`), `catalogueOrder`+`registry` (`internal/steps/catalog.go`), `Kind*` const (`step.go`), `deleteUpstream`+`weaveCollection` (`ensure.go`), `undoRank` (`rollback.go`), the step impl itself, a `stepstest` fixture, a chart definition YAML + `values.yaml` toggle, and a `chart_test.go` case. See the `serviceTemplate` step/`python-git-service` definition for a recent full example.
- Chart `definitions/*.yaml` guard clauses must default-guard each map level (`((.Values.definitions | default dict).<x> | default dict).enabled`), not `.Values.definitions.<x>.enabled` directly — `helm upgrade --reuse-values` against a release installed before that definition key existed panics with "nil pointer evaluating interface {}.enabled". Also: `--reuse-values` does NOT pick up a brand-new `definitions.<x>` chart default on an existing release — pass `--set definitions.<x>.enabled=true` explicitly when enabling a new definition on an already-installed release.
- `api.auth.audience` (`AUTH_AUDIENCE`) is NOT optional in practice despite the values.yaml comment: an
  empty value makes `TokenReviewAuthenticator` omit `spec.audiences`, and Kubernetes then validates the
  caller's token against the **apiserver's own default audience** (`https://kubernetes.default.svc...`),
  not "any audience". fusion-bff's default upstream token (`saToken`, shared with forge/index/content) is
  minted for the custom audience `fusion-bff` (`fusion-bff/deployment/templates/deployment.yaml`'s
  `sa-token` projected volume) — with `AUTH_AUDIENCE` unset, every call from that token fails with
  `invalid token` (401) and Kubernetes' real reason only surfaces via a debug log line (`internal/apiserver/auth.go`'s `Authenticate`, added 2026-09-22:
  logs `tr.Status.Error` on rejection) — the plain 401 response body gives no clue. Confirmed
  experimentally (toggled `AUTH_AUDIENCE` empty vs `fusion-bff` against the same live token): set
  `api.auth.audience=fusion-bff` (or whatever the calling BFF's token audience is) whenever the caller
  uses a custom-audience token rather than its pod's default automounted one.
- Every status field `+optional`, else use `Status().Update()` (required-field `Patch` deadlock, see fusion-flux CLAUDE.md); finalizers via `Patch`, never `Update`
- printcolumn JSONPath has no `length()`; list-map keys (`name`, `key`) must be required fields
- `go mod tidy` prunes deps nothing imports yet — re-run after adding code
- Ledger writes use `conflictBackoff` (30 steps), not `retry.DefaultRetry` (5): shared entries are contended by design and the default failed a 25-writer test
- `stepstest.TriggerJob` is the pre-`app` python-job shape (template + chain + forEach trigger per entrypoint). No chart definition uses it, but the generic engine tests (forEach, ledger sharing, rollback, validation) run on it; `stepstest.PythonJob` is the real `app`-based definition
- Controller/steps tests share `internal/steps/stepstest` fakes; the controller harness injects an `EnvFactory` (`staticEnv`). The fake client needs `WithStatusSubresource(&WizardRun{})` and does not maintain `metadata.generation`
- `forEach` keys are `<step>/<item>` (`etl/load.py` -> key `trigger/etl/load.py`; `stem` keeps directories, so trigger names come out `<job>-etl-load`)
- Mutation-check safety tests from a FRESH copy of the tree each time (a helper that restores only the mutated file lets earlier mutations leak into later runs)
- Docker check: `docker build` with the local daemon (not minikube's), run both binaries with `--help`, then `docker rmi`
- Tests that call `Ensure` need a rig with NO pre-seeded upstream objects if they expect the wizard to own (and delete) them — pre-seeded ones are correctly treated as unowned
- Weave specs are generic `map[string]any` (no import of fusion-weave types); `waitBuild` matches builds by repoUrl+projectDir because forge clears `lastBuildName` on success
- `config/rbac/` and chart RBAC templates are hand-maintained pairs
- Forge's `GitWatcher` reconciler self-heals a build whose index artifact vanished (e.g. deleted by our rollback): it rebuilds on its own next tick, but only once `HEAD` changes or on a brand-new watcher's first reconcile — a dormant repo needs forge's `POST /api/v1/builds/index-drift-cleanup` backstop instead. `waitBuild` retries a missing-artifact build up to `BuildTimeout` instead of failing immediately, to give forge a chance to catch up (verified end-to-end in minikube 2026-09-22)
- E2E in `fusion` against a repo/artifact that already exists (e.g. the old manual `wizard-batch-test-job`, artifact `app.wizard-batch-test-job`): the run's ledger recorded the pre-existing index artifact as `Created`, and its rollback DELETED it from fusion-index, breaking the older manual chain that used it (2026-09-29; cause in `waitBuild`'s ownership handling not yet investigated). Until that is understood, e2e only with a repo/projectDir that nothing else uses, and recover a lost artifact via forge's `POST /api/v1/builds/index-drift-cleanup`
- Never reuse an image tag when redeploying to minikube: even `docker save` + `minikube image load` kept a stale image for a reused tag (the API silently ran old code); use a fresh tag per build (`--set image.tag=...`) and check behaviour, since `docker image inspect` IDs differ between the local and minikube daemons and prove nothing
- `minikube image load <name>:<tag>` (by name) can silently keep a stale cached image even though it reports success; `docker save -o x.tar <name>:<tag>` then `minikube image load x.tar` reliably picks up a rebuilt image
- zsh: `status` is a read-only special var — don't use it as a loop variable (`st=$(...)` instead); unquoted `?` in curl URLs gets glob-expanded ("no matches found") — quote the URL

- `stepstest.Weave` stores Go-typed values (e.g. `int` ports) while real weave JSON decodes to `float64`: read-back helpers (`existingPort`) must accept both, or `matches` falsely reports a conflict only in tests
- Mutation-checking `matches` logic: a prior `Register` stores `SpecHash`, so a ledger-known name is caught by the hash instead; use a freshly `Seed`ed, never-registered upstream object to test `matches` alone. A field that is in both the hash and `matches` is an equivalent mutant if dropped from the hash (e.g. `run`'s `stepKind`), not a test gap
- `stepstest.EventLog` has no `Reset`: record `len(Snapshot())` first and slice afterwards
- New optional step settings go into the ledger hash and `matches` only when set (artifact/image-only mode, trigger `image`, run `stepKind`), so entries written before the setting existed keep their hash
- A parameter `pattern` is also checked against its `default` (`params.ResolveParameters` → `decode`): an optional param with `default: ""` needs a pattern that accepts empty, e.g. `^(…)?$`
- Chart tests (`internal/chart`) shell out to `helm`; in Docker mount it: `docker run --rm -v "$PWD":/src -v /usr/local/bin/helm:/usr/local/bin/helm:ro -w /src golang:1.25 go test -mod=vendor ./...`
- `steps.ValidatesEarly(type, key)` selects which resolved params the API pre-validates at run creation (externalAuth, app params); a new early-validated param needs adding there and to `ValidateAppParams`/`ValidateExternalAuthParams`
- fusion-flux moves fast and unblocked recurring image jobs mid-session (trigger-level `imageOverrides`, `14b1a6f`): check `git log` and `CHANGELOG.md` in `../fusion-flux` before declaring something blocked on weave. Weave's allowlist (`ALLOWED_IMAGE_PREFIXES`) only gates run/trigger `imageOverrides`, never template images, so keep customer images out of templates
- Docker check: the runtime image is distroless (no `sh`); verify with `--entrypoint /api-server --help` and `/manager --help`
- Forge in `fusion`: its Helm release has been `failed` since 2026-09-22 (StatefulSet immutable), and the pods run `fusion-forge:local` (IfNotPresent). Deploy forge changes with `docker build -t fusion-forge:local .` + `docker save` + `minikube image load <tar>` + `kubectl rollout restart` of server/operator/watcher, not `helm upgrade`. Apply GitWatcher CRD changes by hand (`config/crd/bases/`, not Helm-managed)
- E2E with a version bump: create a throwaway repo in the testbed Gitea (`svc/fusion-testbed-gitea`, `gitea:gitea123`, `POST /api/v1/user/repos`; watcher URL `http://fusion-testbed-gitea.fusion.svc.cluster.local:3000/gitea/<repo>.git`), push a copy of `../fusion-testcases/v3-beta/template-wizard-service-streamlit` with a unique `name:`, bump `version:` and push again. Delete the repo afterwards (`DELETE /api/v1/repos/gitea/<repo>`). The autoPromote e2e (2026-10-20) took about 100s from push to tag move and about 20s more to the pod restart
- With `autoPromote`, forge usually tags the first build before the `tag` step runs, so the step records the tag as `FoundUnowned`. That's harmless: rollback deletes the claimed artifact, and the tag goes with it

- Image-wizard e2e (verified 2026-10-06): `fusion`'s weave image predates `imageOverrides`, and weave/wizard CRDs are cluster-wide (`kubectl diff -f .../crds/` first; wizard CRD apply is additive). Build weave from `../fusion-flux` HEAD with a fresh tag, load it with `docker save` + `minikube image load`, install weave (`api.auth.allowUnauthenticated=true`, `imageOverrides.allowedPrefixes`, `ingress.hostSuffix`) and this chart in a throwaway namespace, create `WizardRun`s with `kubectl apply`, and delete the namespace afterwards
- Weave cron schedules are 6-field with seconds first (`0 * * * * *`); a 5-field one is only rejected by weave's trigger reconciler (trigger never `ACTIVE`), so the wizard run still goes Ready. Stock `nginx` crash-loops under weave's read-only-root/non-root workload defaults and weave then stops the run and deletes its Deployment; `registry.k8s.io/pause:3.10.1` is a cached image that stays up for service tests

## Rules
- `fusion-dev-a`/`fusion-dev-b` are Flux-managed — never `helm upgrade` those; e2e in a disposable namespace. `fusion` itself is non-Flux, the user's own dev/test instance — direct `helm upgrade`/deploys there are fine (confirmed 2026-09-22)
- CHANGELOG entry (Keep a Changelog, `## [x.y.z] — YYYY-MM-DD`) before every commit; bump chart `version`/`appVersion` on release
- Branch is `main`; ask before commit/push; no Claude co-author trailer; SPDX header on every `.go` file
